# Vietnam ride-hailing services: booking on behalf of a named rider (AND-98)

## Question

Can a third-party web app start or book a ride in Vietnam for a named rider (someone other than
the app operator), where the constraint is: **the end-rider must be the payer of record.** The
calling app/business can never be the payer of record — if the only available route requires the
calling business to be billed/invoiced, that route is unusable for our purposes.

This document checks five services — Grab, Be, Xanh SM, Mai Linh, Vinasun — against four separate
questions: (1) a documented booking API, (2) deep links / universal links that pre-fill a
destination, (3) corporate "for Business" programs that let a company arrange a ride for a guest,
and (4) terms-of-service restrictions on third-party-initiated bookings. It also records what
format the destination must take (plain text address, lat/lng, or a place ID) for each usable
route.

## Summary

- **Grab**: The only service with a route that plausibly satisfies the payer-of-record constraint end to end. Its Farefeed API response (or a hand-constructed equivalent) yields a vendor-documented `grab://open?...` deep link with lat/lng destination pre-filled, which opens the **rider's own Grab app** for the rider to confirm and pay — this is the strongest deep-link-hand-off candidate of the five services. Separately, Grab For Business Concierge can be configured for guest cash/QR self-pay, satisfying the constraint too, but that option is documented specifically for **hotel** clients and is not confirmed for a non-hotel venue, and Concierge itself is a human-staffed portal, not an API. **Verdict: usable, with the deep-link route being the best fit for an automated hand-off; the Concierge cash/QR route is a usable fallback pending confirmation it's offered to non-hotel accounts.**
- **Be**: No ride-booking API and no documented deep link exist. beCorporate is company-invoiced for employee travel (violates the constraint). The consumer-level "đặt hộ" (book-for-someone-else) feature lets any Be user book a named rider who need not have the app, but who pays (booker's account vs. rider-pays) is not established from a primary source — this is the key unresolved fact for Be. Be's ToS also explicitly forbids third parties "creating Internet paths that link to the Be application," which is a real obstacle to a deep-link approach even if a scheme existed. **Verdict: not usable as documented; no deep-link candidate exists at all, and the one potentially-viable route (đặt hộ) has an unresolved payer question.**
- **Xanh SM (Green SM)**: No booking API, no deep link (official or informal) found anywhere. Xanh Business is company-invoiced (violates the constraint). The consumer "Xanh Family" feature books for a named family member but is not documented as usable by a third-party app on a stranger's behalf. **Verdict: not usable as documented; no deep-link candidate exists.**
- **Mai Linh**: No booking API, no deep link. The corporate GreenCard/MPass program is company-invoiced (violates the constraint). The only route that actually satisfies the payer-of-record constraint is the **1055 phone hotline**, where the caller gives pickup/destination verbally and whoever is in the car pays — but this is a human phone call, not automatable, and not a deep link. **Verdict: not usable for an automated flow; the hotline is a manual fallback only.**
- **Vinasun**: Same shape as Mai Linh — no booking API, no deep link, a company-invoiced corporate card program (violates the constraint), and a phone hotline that satisfies the payer constraint but only as a manual, human-operated call. **Verdict: not usable for an automated flow; the hotline is a manual fallback only.**

**Overall**: Grab is the only service worth building a deep-link hand-off against, because it is the only one with a currently-live, vendor-documented deep link (`grab://open?...`) that pre-fills a destination and opens the rider's own app for the rider to pay. None of the other four services publish any deep link at all, official or informal. If the map's fallback plan is "deep-link hand-off with destination pre-filled," Grab is the only service where that plan has a concrete, vendor-sourced implementation path today; for Be/Xanh SM/Mai Linh/Vinasun, the equivalent fallback would have to be a plain "open the app / call this number" hand-off with no destination pre-fill, since no deep-link mechanism was found for any of them.
