# Zalo in-app webview: WebRTC, service worker, and push feasibility

Research pass conducted 2026-09-09.

## Scope and relationship to prior research

This document fills a specific gap left by a prior ticket (AND-61): the claim "WebRTC does not work inside in-app browsers (Zalo/Facebook/Messenger webviews) on iOS" was not primary-sourced at the time. It is about the **plain in-app browser** Zalo opens when a Player taps an ordinary shared link (e.g. a booking link pasted into a Zalo chat) — not the registered **Zalo Mini App** platform, which is a distinct product with its own SDK and its own JS bridge. Where the research below found Mini-App-specific material, it is labeled as such and kept separate.

The following facts are taken as already established in `docs/research/web-app-ringing.md` and are not re-derived here:
- iOS web push requires a Home Screen install (iOS/iPadOS 16.4+), roughly 5 user actions (Source: https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).
- Android Chrome and desktop browsers need no install step for web push.
- A web push is at best an ordinary system notification; there is no web equivalent of PushKit/CallKit, and Android's `USE_FULL_SCREEN_INTENT` is unreachable from a browser tab.
- Requirements are VAPID keys + a registered service worker + a web app manifest; delivery itself is free at the protocol level.

## Q1. `RTCPeerConnection` / `getUserMedia` inside Zalo's webview, and User-Agent detection

### iOS

- Since 2020, Apple's App Store Review Guidelines require that "Apps that browse the web must use the appropriate WebKit framework and WebKit JavaScript" (with an EU/Japan-only entitlement to use an alternative engine, which does not apply to a Vietnam-market app like Zalo) (Source: https://developer.apple.com/app-store/review/guidelines/, guideline 2.5.6). This confirms the working assumption from AND-90's brief: **Zalo's iOS in-app browser is necessarily a WKWebView instance** (the older UIWebView has been deprecated/removed by Apple and would not satisfy this guideline). We did not find a source naming Zalo's WKWebView version directly — see Q5 and Gaps.
- WKWebView itself has supported `getUserMedia`/WebRTC since iOS/iPadOS 14.3. This is confirmed by WebKit's own bug tracker: bug 208667, "getUserMedia does not work in WKWebView-based browsers like Chrome, Firefox," is marked **RESOLVED / CONFIGURATION CHANGED**, with the fix landing in iOS 14.2–14.3 (Source: https://bugs.webkit.org/show_bug.cgi?id=208667). Before that fix, `getUserMedia` worked only in Safari proper and Home-Screen web apps, not in any third-party WKWebView-based browser.
- That WebKit-level support is not automatic for every embedding app. To reach it, the host app must declare `NSCameraUsageDescription`/`NSMicrophoneUsageDescription` in its `Info.plist` (the standard iOS camera/microphone permission strings) and grant capture at the AVFoundation level; a secondary developer write-up describes this configuration step in detail, but we could not confirm the exact mechanism from an Apple primary source since the corresponding Apple documentation pages returned only their title through automated fetching, not full body text (Source, secondary/unverified against a primary page: https://solarana.dev/2021/01/01/camera-and-microphone-in-wkwebview/; the corresponding Apple page we could not read the body of: https://developer.apple.com/documentation/bundleresources/information-property-list/nscamerausagedescription).
- Starting iOS 15, Apple added a `WKUIDelegate` method (`webView(_:requestMediaCapturePermissionFor:initiatedByFrame:type:decisionHandler:)`) that lets the host app intercept and programmatically grant/deny/skip the camera-mic prompt for trusted content, instead of relying on the default system prompt (Source, Apple's own WWDC 2021 session transcript: https://developer.apple.com/videos/play/wwdc2021/10032/). This is an optional API — a host app that implements nothing still gets the standard OS-level permission prompt as of iOS 14.3, per the bug 208667 resolution above, but a host app that *does* implement this delegate could choose to deny media capture for its embedded webview.
- **Whether Zalo's iOS app has declared the camera/microphone usage strings and how (or whether) it implements the iOS 15 delegate is not documented anywhere Zalo publishes**, and Zalo is closed-source — this is a hard gap (see Gaps section).
- A real, but unattributed, complication: an Apple Developer Forums thread reports that `getUserMedia({audio: true})` specifically (not video) began failing inside in-app browsers (tested against LinkedIn's in-app browser) on iOS 15.1+, while it continued to work in Mobile Safari, Chrome for Android, and had worked in the same in-app browser on iOS 14.5.1–15.0.1. No WebKit engineer or Apple staff attributed a root cause in the thread; one reply speculated it was a TURN-server/networking issue rather than a permissions issue (Source, developer forum — not an official statement, flagged as a softer signal: https://developer.apple.com/forums/thread/699479). This is the only source found that speaks *directly* to "WebRTC breaking specifically in an in-app browser on iOS," and it does not settle whether the cause is WebKit-wide, sandboxing-specific, or an artifact of that particular app's WKWebView configuration.
- **User-Agent detection**: Zalo's iOS webview does self-identify. Observed UA strings captured in a public database include tokens such as `Zalo iOS/470 ZaloTheme/light ZaloLanguage/vn` appended to a standard Mobile Safari WKWebView UA string (e.g. `Mozilla/5.0 (iPhone; CPU iPhone OS 15_5 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Mobile/15E148 Zalo iOS/470 ZaloTheme/light ZaloLanguage/vn`). This is an observational/crowd-sourced database, not a Zalo or Apple document, so it is a softer signal, but it is consistent across multiple captured strings (Source, secondary/observational: https://user-agents.net/platforms/ios/user-agents and related string pages under that domain).

### Android

- Android's system WebView component (Chromium-based) has supported `getUserMedia`/WebRTC for years at the platform level, but camera/microphone access must be explicitly granted by the *host app* via `WebChromeClient.onPermissionRequest()` — the host app receives a `PermissionRequest` naming `RESOURCE_VIDEO_CAPTURE`/`RESOURCE_AUDIO_CAPTURE` and must call `request.grant(...)`. We confirmed the class and constant names exist in the official Android reference (Source: https://developer.android.com/reference/android/webkit/PermissionRequest and https://developer.android.com/reference/android/webkit/WebChromeClient), though automated fetching of these reference pages returned only page chrome/navigation and not the full method-level documentation body — the class/constant names and the general grant flow are corroborated by multiple independent developer write-ups and a Google sample app (Source, secondary but converging: https://github.com/googlesamples/android-permissionrequest, https://www.javathinking.com/blog/allowing-microphone-access-permission-in-webview-android-studio-java/).
- **Whether Zalo's Android app actually implements `onPermissionRequest` and grants camera/mic to its in-app webview is undocumented** — Zalo's Android app is closed-source and publishes nothing about this. This is a hard gap (see Gaps section), symmetrical to the iOS gap above.
- **User-Agent detection**: Zalo's Android webview clearly self-identifies. An observed UA string is `Mozilla/5.0 (Linux; Android 12; 2201117TG Build/SKQ1.211103.001;) AppleWebKit/537.36 (KHTML, like Gecko) Version/4.0 Chrome/109.0.5414.117 Mobile Safari/537.36 Zalo android/12100676 ZaloTheme/dark ZaloLanguage/vi` (Source, secondary/observational database: https://user-agents.net/string/mozilla-5-0-linux-android-12-2201117tg-build-skq1-211103-001-applewebkit-537-36-khtml-like-gecko-version-4-0-chrome-109-0-5414-117-mobile-safari-537-36-zalo-android-12100676-zalotheme-dark-zalolanguage-vi). The `Version/4.0 ... Chrome/109...` combination is the classic Android System WebView signature (native Chrome UAs omit the `Version/X.Y` token), and the appended `Zalo android/<build>` token is the clear, page-detectable Zalo identifier. This is again a crowd-sourced/observational source, not Zalo's own documentation, so treat the specific Chromium version number as a snapshot from one device, not a guaranteed constant across all Zalo installs.

**Net for Q1**: a page can reliably detect "I am running inside Zalo's in-app browser" via the User-Agent string on both platforms (the `Zalo iOS/...` and `Zalo android/...` tokens). Whether `getUserMedia` actually succeeds once detected is a host-app-configuration question on both platforms, and Zalo has published nothing confirming or denying that its app grants the needed permissions to its embedded webview — this is the central unresolved point behind the AND-61 claim (see verdict section below).

## Q2. Service Worker registration and Web Push inside Zalo's webview

### iOS

- WKWebView does not get generic, always-on Service Worker support the way Safari does. A long-open WebKit bug ("WKWebView support for Service Workers," status **NEW**, i.e. still unresolved as a general capability) documents that Service Workers in a third-party WKWebView require a special, non-public entitlement (`com.apple.developer.WebKit.ServiceWorkers`) in addition to being restricted to the app's declared "App-Bound Domains" — and that this entitlement is reported not to work reliably even when developers do have it (per developer comments in the thread, it can work in the Simulator but fail on real devices because the entitlement cannot be added through the ordinary Apple certificates portal) (Source, WebKit bug tracker, status NEW / unresolved, developer comments not an official Apple statement: https://bugs.webkit.org/show_bug.cgi?id=206741).
- Apple's own WebKit blog post introducing "App-Bound Domains" (the up-to-10-domain allowlist mechanism, iOS/iPadOS 14.0+) explains that the *host app*, not the website, declares the list: "Applications that opt-in to this new feature can specify up to 10 'app-bound' domains using a new Info.plist key — `WKAppBoundDomains`" (Source: https://webkit.org/blog/10882/app-bound-domains/). The post itself does not mention Service Workers — it describes the feature as unlocking JavaScript evaluation, user script injection, message handlers, and cookie manipulation via `WKHTTPCookieStore`.
- The link between Service Workers and App-Bound Domains specifically is confirmed in the bug-tracker thread itself, by two independent WebKit contributors: "I think this issue can be closed by documenting that Service Workers would only work with App-Bound Domains" (comment 4), and a later commenter confirming empirically, "Trialling this today with AppBoundDomains set, navigator.serviceWorker is exposed" (comment 5) (Source: https://bugs.webkit.org/show_bug.cgi?id=206741). So Service Worker registration in a third-party WKWebView requires the page's own domain to be inside that app's fixed, ≤10-entry, Info.plist-declared domain list — on top of whatever entitlement question the rest of that thread leaves open.
- This turns the Zalo question from merely undocumented into structurally implausible for *this specific app*: Zalo's plain in-app browser exists to open arbitrary links Players paste or receive in chat — it cannot pre-declare every possible domain a user might tap, and a small pickleball-booking site has no relationship with Zalo that would give it a reserved slot in Zalo's own ≤10-domain app-bound list. Unless Zalo has, unusually, added this specific site's domain to its own Info.plist (something only Zalo could do, and nothing found suggests any app does this for arbitrary third-party sites), Service Worker registration for the booking app inside Zalo's general-purpose webview is ruled out by how App-Bound Domains works, not merely unconfirmed. We treat this as the primary-sourced answer for Q2/iOS; whether Zalo separately holds the `com.apple.developer.WebKit.ServiceWorkers` entitlement is now a secondary, moot question given the domain-list constraint.
- **This is a second, independent reason iOS push in Zalo's webview is moot, on top of the primary reason already established in `web-app-ringing.md`**: iOS web push requires a Home Screen install regardless, and a Home Screen install is a Safari-only mechanism (see Q3) — so even if the App-Bound Domains constraint above were somehow cleared, the install requirement alone still blocks push from inside the webview.

### Android

- Android's system WebView (Chromium-based) does support standard Service Worker *registration* — a Chromium engineer (Richard "Torne" Coles) states plainly, "Service Workers have been supported for many releases," in an official Chromium discussion group thread, with an earlier report in that same thread turning out to be a device-specific problem, not a platform limitation (Source, Chromium team member, official chromium.org Google Group — authoritative but informal, not a docs page: https://groups.google.com/a/chromium.org/g/chromium-discuss/c/EnEjyoJRrr8/m/AiuP240MBwAJ).
- However, Android WebView does **not** support the Web Push API. A Chromium/Google engineer (Thomas Steiner) states directly, "WebView does not support the Web Push Notification APIs," in the official `service-worker-discuss` Google Group for chromium.org (Source, Chromium/Google team member, official chromium.org Google Group — authoritative but informal: https://groups.google.com/a/chromium.org/g/service-worker-discuss/c/2-G9PwduokQ). We could not additionally confirm this via the Chromium issue tracker itself (`issues.chromium.org/issues/40388442`, titled "Implement Push API and Notifications in WebView") because that tracker required sign-in and returned only its login page to automated fetching — flagged as an unreached source.
- Net: a page loaded inside Zalo's Android in-app browser can register a Service Worker, but calling `pushManager.subscribe()` on that registration will not work, because the underlying Android System WebView component does not implement the Push API at all — independent of anything Zalo itself does or doesn't configure. This is a platform-level (Android WebView) limitation, not a Zalo-specific one.

**Net for Q2**: Web Push cannot work inside Zalo's Android webview because the underlying WebView component itself lacks the Push API — a firm, engineer-confirmed platform limitation, independent of Zalo. On iOS, Web Push inside the webview is blocked doubly: Service Worker registration for this specific site requires the site's domain to be one of Zalo's own ≤10 pre-declared App-Bound Domains, which a general-purpose link-opening browser structurally cannot offer to an unaffiliated third-party site; and, regardless, the Home Screen install requirement (established in `web-app-ringing.md`) cannot be completed from inside the webview at all (see Q3).

## Q3. Home Screen install and hand-off to the system browser

- Home Screen install ("Add to Home Screen") on iOS is a Safari-menu action. We found no source — Apple's or Zalo's — describing an "Add to Home Screen" affordance inside any third-party WKWebView's UI chrome, including Zalo's. This is a gap, not a confirmed absence (see Gaps).
- Zalo does publish (via independent, converging Vietnamese consumer-tech blogs, not Zalo's own developer docs) a **global app setting** that changes how *all* links behave: Zalo app → Cá nhân (Personal) → Cài đặt (Settings, gear icon) → Quyền riêng tư (Privacy) → Tiện ích (Utilities) → "Chọn cách mở link" (Choose how to open links) → "Mở bằng trình duyệt web" (Open with web browser). Once turned on, tapping an external link in Zalo opens it directly in the phone's default browser instead of Zalo's in-app webview. These same sources note the setting does **not** apply to Zalo's own Mini App / ZaloPay / Zalo Shop links, which always stay in-app regardless (Source, converging independent secondary sources, not Zalo's own documentation — flagged as a softer signal: https://quantrimang.com/cong-nghe/cach-mo-link-tren-zalo-bang-trinh-duyet-199742, https://fptshop.com.vn/tin-tuc/thu-thuat/cach-de-mo-lien-ket-tren-zalo-bang-trinh-duyet-web-164518, https://vuhoangtelecom.vn/cach-mo-link-tren-zalo-bang-chrome/, https://mytour.vn/vi/blog/bai-viet/thu-thuat-mo-link-zalo-tren-chrome-tren-dien-thoai-cuc-ky-de-dang.html).
- This setting is a **global, user-controlled default that has to already be turned on before the Player ever taps the booking link**. It is not something the booking web page can trigger on demand, and it is off by default (the existence of these how-to articles teaching people to turn it on implies the default is "open in Zalo's webview"). We could not confirm the default state from a Zalo primary source — flagged as a gap.
- A search for a **per-link, in-the-moment "Open in browser" affordance** (the kind of "..." menu option Facebook's in-app browser is known for) turned up only a search-result summary asserting such a menu exists with unspecified options ("tùy chọn để quản lý cách hiển thị và mở link") — we could not verify its exact wording or that it includes a direct browser hand-off option, because the underlying Zalo community pages are client-rendered SPAs that returned only their page title to automated fetching (same resistance to fetching noted for `developers.zalo.me` in the prior research pass — see Gaps). This is a genuine gap, not a confirmed feature.
- We looked for a **programmatic** hand-off mechanism a web page itself could trigger (universal links, `intent://` URLs, a Zalo-specific JS bridge call) and found no documentation of one. The closest evidence is indirect and negative: a Zalo developer-community post titled "Không thể chuyển hướng tới app momo từ zalo webview" ("Cannot redirect to the Momo app from Zalo's webview") suggests that even app-to-app deep-linking out of Zalo's webview is unreliable in at least some cases, which weighs against assuming a web page can reliably force its way out to the system browser (Source, Zalo developer community, title/topic only — full post body not retrievable, SPA: https://developers.zalo.me/community/detail/4899917dad3844661d29).

**Net for Q3**: The only documented way to leave Zalo's in-app webview for the system browser is the pre-existing global "Open with web browser" app setting, which the Player would need to have already turned on beforehand — the booking page cannot flip it for them, and it is off by default. A per-link menu option to "Open in browser" is plausible (common in comparable apps) but not documented for Zalo specifically. No programmatic/deep-link hand-off is documented, and there is anecdotal evidence that deep-linking out of Zalo's webview is unreliable in at least the Momo-app case.

## Q4. Step count from tapping a Zalo-shared link to a possible first push

All counts below assume the "..." per-link "Open in browser" menu option exists as commonly seen in comparable in-app browsers (LinkedIn, Facebook); this specific affordance is **not confirmed for Zalo** (see Q3), so mark every count below as conditional on that gap being resolved in Zalo's favor. If that affordance does not exist, the only documented path is the pre-existing global "Open with web browser" setting, which removes the in-app-webview step entirely but requires the Player to have configured it in Zalo's settings before ever tapping the link (an action outside this flow, so it isn't counted below).

### iOS (assuming the "..." → open-in-Safari menu affordance exists)

1. Tap the Zalo-shared link (opens Zalo's in-app WKWebView).
2. Tap the "..." (or share) menu inside Zalo's webview.
3. Tap "Open in Safari" (or equivalent) — hands off to Safari, per the established requirement that Home Screen install can only happen from Safari.
4. In Safari, tap the Share sheet icon.
5. Tap "Add to Home Screen" in the share sheet.
6. Tap "Add" to confirm — this completes the roughly-5-action Home Screen install already established in `docs/research/web-app-ringing.md` (steps 4–6 here map onto that established sequence; step 3, the Zalo hand-off, is additional and specific to this flow).
7. Return to the Home Screen and tap the newly installed app icon to actually launch it as a standalone PWA (a push subscription registered from inside Safari's tab context is not guaranteed equivalent to one registered from the installed PWA's own service-worker scope — the established research says the install is required before push works, implying the Player must open the installed icon at least once).
8. Inside the installed PWA, take whatever in-page action triggers the push permission request (e.g., tap "Enable notifications").
9. Tap "Allow" on the native iOS notification permission prompt.

**Total: 9 user actions on iOS**, before a push could possibly arrive — and that is *before* accounting for the App-Bound Domains blocker from Q2 (which, per that section, rules out push from inside the webview regardless of step count), and conditional on the unconfirmed Zalo "open in Safari" menu item existing at all.

Note on step count vs. `web-app-ringing.md`: that document counts the Safari-side install as "~5" actions (open Safari, Add to Home Screen, open from icon, trigger permission, Allow). This document's steps 4–6 split "tap the Share-sheet icon," "tap Add to Home Screen," and "tap Add to confirm" into three separate taps rather than one, because this document is counting every discrete tap rather than grouping the Share-sheet flow as one action. The two documents are not in conflict — this one is simply more granular, plus it adds one extra step (step 3) for the Zalo-to-Safari hand-off that does not exist in the plain-Safari case `web-app-ringing.md` was scoped to.

### Android (Chrome needs no install step, per prior established research)

1. Tap the Zalo-shared link (opens Zalo's in-app webview).
2. Tap the "..." (or share) menu inside Zalo's webview.
3. Tap "Open in Chrome" (or equivalent) — hands off to Chrome.
4. Inside Chrome, take the in-page action that triggers the push permission request.
5. Tap "Allow" on Chrome's native notification permission prompt.

**Total: 5 user actions on Android**, before a push could possibly arrive — conditional on the same unconfirmed Zalo menu affordance, but not blocked by any install step, consistent with Android Chrome needing no Home Screen install for web push (established in the prior research pass).

Both counts are step-count exercises built on the established install/no-install facts plus the unconfirmed Zalo hand-off affordance from Q3; they are not counts anyone has verified by walking a real device through the flow (see Gaps).

## Q5. Zalo's webview engine, version, and documented limitations

- Zalo publishes a general developer portal at `developers.zalo.me` and a separate **Zalo Mini App** platform with its own docs at `mini.zalo.me/docs/api/` (redirects to `miniapp.zaloplatforms.com/docs/api/`) (Source: redirect observed directly, https://mini.zalo.me/docs/api/ → https://miniapp.zaloplatforms.com/docs/api/). Zalo Mini Apps are described (via search-result summaries, not a fetched primary page) as running inside "the Zalo Webview" and communicating with the native Zalo app over a JavaScript bridge, built entirely on HTML/CSS/JS (Source, search-result summary of miniapp.zaloplatforms.com content, not independently fetched in full — softer signal). This confirms Zalo has an internal name ("Zalo Webview") for its embedded browser component, but we could not retrieve a page stating its underlying engine version, wrapper library, or build details — every specific API page we tried to fetch directly (`openWebview`, the Mini App intro, and multiple `developers.zalo.me/community` threads) returned only the page's `<title>`, because these are client-rendered single-page applications that do not serve content to a plain fetch — the same behavior the prior research pass reported for the main developer docs site. This is a direct, repeated confirmation of that earlier finding, now also shown to extend to Zalo's community/support pages, not just its API reference pages.
- No SDK/docs page was found describing a specific WebView/WKWebView version, Chromium build baseline, or wrapper library (e.g. no evidence Zalo uses a third-party wrapper like Crosswalk or a custom Chromium fork). The only version-adjacent signal is indirect: observed User-Agent strings (see Q1) show Zalo's Android webview reporting `Chrome/109.0.5414.117`, which is the Chromium version baked into the Android System WebView component installed on that particular test device at capture time — this is a property of the device's separately-updated system WebView, not something Zalo controls or version-locks, and will vary across devices and over time. No comparable version marker exists in the iOS UA strings beyond the OS version itself, consistent with WKWebView not exposing its own version number distinct from the OS's WebKit build.
- Zalo separately operates **Zalo Notification Service (ZNS)**, a business-to-customer messaging product where an Official Account (OA) sends templated notifications to Zalo users via a server-to-server API (Source: https://developers.zalo.me/docs/zalo-notification-service/bat-dau/gioi-thieu-zalo-notification-service-api). This is unrelated to Web Push and does not run through a Service Worker or the in-app browser at all — it requires a registered, approved OA business account and pre-approved message templates, and delivers into the Zalo app's own chat/notification surface, not to an arbitrary web page a Player has open. It is not a substitute for, or evidence about, Web Push capability inside Zalo's webview; noted here only to avoid it being confused with the Web Push question this document addresses.

## AND-61 verdict: is "WebRTC does not work inside Zalo's webview on iOS" now settled?

**Still unsettled — revised from a blanket claim to a conditional, platform-configuration-dependent one.**

- What is now primary-sourced and confirmed: WKWebView itself (the engine Zalo's iOS in-app browser is required to use, per App Store guideline 2.5.6) has supported `getUserMedia`/WebRTC since iOS 14.3, at the WebKit engine level (bugs.webkit.org 208667, RESOLVED CONFIGURATION CHANGED). So the original claim, read literally as "the WKWebView engine cannot do WebRTC," is **refuted** as a platform-wide statement.
- What is not settled: whether *Zalo's specific app* has done the additional, app-side configuration WKWebView requires for that engine capability to actually work in its webview — declaring `NSCameraUsageDescription`/`NSMicrophoneUsageDescription`, and not denying capture via the iOS 15 `WKUIDelegate` media-capture-permission method. Zalo publishes nothing on this, and Zalo's app is closed-source, so this cannot be settled from documentation. There is also an unattributed, unresolved forum report of `getUserMedia({audio:true})` specifically breaking inside in-app browsers (not Zalo-specific; tested against LinkedIn's) on iOS 15.1+, which could be read as weak circumstantial support for the original AND-61 claim, but its cause was never identified in that thread and it does not name Zalo.
- Even if Zalo's webview does support `getUserMedia`, the practical case for this ticket is moot for two different, better-sourced reasons: (a) iOS Web Push requires a Home Screen install (established in `web-app-ringing.md`), and no path from inside Zalo's webview to a Home Screen install exists without first handing off to Safari (Q3); and (b) independent of that, Service Worker registration for this specific site inside Zalo's webview is ruled out by how App-Bound Domains works (Q2) — a general-purpose link-opening browser cannot pre-declare an unaffiliated third-party site among its own ≤10 fixed domains. So a call/notification feature relying on Web Push cannot function purely inside Zalo's webview on iOS regardless of how the WebRTC question resolves.

**On Android**, the original claim was scoped to iOS only, so it makes no assertion to confirm or refute there; our own findings (Q1/Q2) show Android's WebView-level WebRTC support is real but similarly gated behind the host app calling `onPermissionRequest`, and that Android WebView's lack of the Web Push API is a firm, engineer-confirmed platform limitation independent of Zalo.

## Gaps / open questions

Each item below is a gap — a claim that could not be settled from documentation — not a guess.

1. **Zalo's own developer site resists fetching.** `developers.zalo.me` (root and `/docs`), `mini.zalo.me/docs/api/` → `miniapp.zaloplatforms.com/docs/api/`, the `openWebview` API page, and multiple `developers.zalo.me/community/detail/...` and `miniapp.zaloplatforms.com/community/...` threads all returned only their page `<title>` to automated fetching (WebFetch), never full body content — these are client-rendered SPAs. This reproduces, and extends to community/support pages, the exact resistance the prior research pass reported for the docs site. **No workaround was found**; this is an explicit, repeated gap, not filled by any secondary source for Zalo-specific technical claims.
2. **Whether Zalo's iOS app declares camera/microphone usage-description keys, and whether/how it implements the iOS 15 `WKUIDelegate` media-capture-permission delegate.** Undocumented; Zalo is closed-source. **Minimal device test**: host a debuggable page with a `getUserMedia({video:true, audio:true})` button and a visible console log at an HTTPS URL, share that URL in a Zalo chat on an iPhone (iOS 16+), tap the link, tap the button inside Zalo's webview, and use Safari's remote Web Inspector (connect the iPhone to a Mac, Safari → Develop → [device] → [Zalo's WKWebView tab, if it is inspectable at all]) to see whether a native permission prompt appears or an error is thrown immediately.
3. **Whether Zalo's Android app implements `WebChromeClient.onPermissionRequest` and grants camera/mic to its embedded WebView.** Undocumented; Zalo is closed-source. **Minimal device test**: same test page as above, shared and tapped inside Zalo on an Android phone; use `chrome://inspect` from a desktop Chrome connected via USB debugging to inspect the Zalo webview's console output and see whether a permission prompt or an immediate `NotAllowedError` occurs.
4. **Root cause of the iOS 15.1+ in-app-browser `getUserMedia({audio:true})` regression** reported in the Apple Developer Forums thread was never identified there, and the thread does not test Zalo specifically. Unresolved by documentation; would need the same kind of remote-inspector device test as above, run specifically against Zalo, to know if it reproduces.
5. **Whether Zalo's webview UI exposes a per-link "..." → "Open in browser" menu option**, analogous to Facebook's/LinkedIn's in-app browsers.
