# Desk Page Alerts: Sound, Badge, Throttling, and Streaming Facts

This research feeds [AND-83](https://linear.app/andie-monterro/issue/AND-83), a child of [AND-82](https://linear.app/andie-monterro/issue/AND-82) "Wayfinder map: Desk Thread." The question behind it: the Staff desk is a desktop browser tab that stays open all day, often sitting behind other tabs. If a poll or a stream tells that page new data arrived while it is backgrounded, what can the page actually do to get a staff member's attention (sound, title/favicon badge), and how late might that attention-getting be, given documented browser throttling? This is a fact sheet only. It does not recommend polling vs. SSE, and it does not recommend a notification design — it exists so that decision can be made with facts in hand.

## Note on method

Every claim below carries an inline `(Source: URL)` pointing at the primary page it came from — a browser vendor's own docs or blog (developer.chrome.com, web.dev, developer.mozilla.org, webkit.org/blog, chromium.org), a W3C/WHATWG spec, or Vercel's own docs. Secondary write-ups (blog aggregators, SEO comparison sites, Stack Overflow) were used only to find where to look, never cited as the source of a fact. Where a WebSearch summary was the only way a claim surfaced, and no direct fetch of the primary page could confirm the exact wording, that is stated as a gap in the closing section rather than presented as settled fact. Several of the primary pages themselves are silent on parts of this ticket's exact question (e.g., whether a setting survives reload) — those silences are also called out as gaps rather than filled in with inference presented as fact.

## 1. Sound

### Can a background poll play a sound if the user clicked earlier in the session?

**Chrome/Edge (Chromium).** Chrome blocks autoplay of audio **with sound** unless one of two things is true: the user has interacted with the domain (click, tap), or the site has built up a high **Media Engagement Index (MEI)** score from past visits. Muted autoplay is always allowed regardless. (Source: https://developer.chrome.com/blog/autoplay/) Concretely, Chromium's own project page states the gesture that counts is broad: "Any click on the document itself (this excludes scrolling) will count as user interaction." (Source: https://www.chromium.org/audio-video/autoplay/)

This means: yes — if the staff member has clicked anywhere on the desk page earlier in the session (to open a thread, click a button, anything that isn't a scroll), a later `new Audio().play()` or Web Audio `start()` triggered by a poll result, with no gesture of its own, is allowed to play with sound. Chrome's guidance for developers who don't want to track this bit at all: "I'd recommend you stick to `click` for the time being," while noting "events that trigger user activation are still to be defined consistently across browsers." (Source: https://developer.chrome.com/blog/autoplay/) Chrome's Web Audio autoplay post separately shows a code snippet of the events it listens for in its own example to auto-resume an `AudioContext` — `click, contextmenu, auxclick, dblclick, mousedown, mouseup, pointerup, touchend, keydown, keyup` — that is an example listener list in a code sample, not a documented, exhaustive policy list of every event Chrome treats as an activating gesture. (Source: https://developer.chrome.com/blog/web-audio-autoplay)

**Web Audio API specifically.** If an `AudioContext` is created before any user gesture, it starts in the `suspended` state and needs an explicit `resume()` call after a gesture; alternatively, creating the `AudioContext` only after a gesture avoids this altogether. Chrome also auto-resumes a suspended context the moment both (a) the user has interacted with the page and (b) `start()` is called on a source node. (Source: https://developer.chrome.com/blog/web-audio-autoplay)

**Edge.** Edge is Chromium-based and its own admin-policy documentation for `AutoplayAllowed` confirms the same two-state model at the policy level ("Allow" vs. "Limit," where Limit means "autoplay is limited to webpages with high media engagement or active WebRTC streams") — no separate Edge-specific gesture or MEI mechanism is documented; this is Chrome's mechanism applied to Edge's Chromium engine. (Source: https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/autoplayallowed) No Edge-specific autoplay blog post (equivalent to Chrome's or WebKit's) was found; this is inherited Chromium behavior, not independently documented by Microsoft in the way Chrome documents its own MEI mechanism.

**Firefox.** MDN's autoplay guide states the general cross-browser rule (not Firefox-specific wording): media is allowed to autoplay only if at least one of — it's muted/silent, "the user has interacted with the site (by clicking, tapping, pressing keys, etc.)," or the site is on an allowlist. (Source: https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay) The same page documents two Firefox preferences directly relevant to a backgrounded desk tab: `media.block-autoplay-until-in-foreground` (default `true`) — "A Boolean preference which indicates whether media playback is blocked when started on a background tab," where the default "means that even when otherwise available, autoplay won't take place until after a tab is brought to the foreground. This prevents the distracting situation in which a tab begins playing sound and the user can't find the tab" — and `media.autoplay.block-webaudio` (default `true`) — "indicates whether to apply autoplay blocking to the Web Audio API... audio contexts are only able to play on pages once there has been Sticky activation." (Source: https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay) Whether `media.block-autoplay-until-in-foreground` blocks *only* audio started while a tab has never yet been foreground, versus also re-blocking a poll-triggered `Audio.play()` in a tab that was foregrounded earlier in the session and is now backgrounded again, is not resolved by this page's wording — see Gaps. This preference is the clearest documented signal, of any browser covered here, that a backgrounded tab specifically (not just an un-gestured page) can face an extra autoplay block on Firefox's own defaults.

**Safari/WebKit.** WebKit's autoplay policy blog post states Safari (from macOS High Sierra on) "uses an automatic inference engine to block media elements with sound from auto-playing by default," and its guidance to developers is blunt: "Websites should assume any use of `<video>` or `<audio>` requires a user gesture click to play." (Source: https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/) The post recommends checking the Promise returned by `play()` to detect a block and fall back to manual controls, rather than presuming a gesture will be remembered. WebKit's later, separate post on the general User Activation API describes Safari's gesture model in the same terms used elsewhere in this section — "transient activation" (starting an internal timer lasting "a few seconds, maybe" from a qualifying event) versus "sticky activation" (true once the page "has had transient activation at some point in the past") — triggered by `keydown` (excluding Escape/reserved keys), `mousedown`, `pointerdown` (mouse), `pointerup` (non-mouse), or `touchend`, and scoped "to the entire window (or browser tab)." (Source: https://webkit.org/blog/13862/the-user-activation-api/) That post is about the general activation primitive used by several APIs (Web Share, `window.open()`, Payment Request, Web Notifications) and does not itself connect this mechanism to Safari's autoplay policy by name, nor does it address whether the state survives a reload — so it corroborates the shared gesture vocabulary but does not close the reload question for Safari either.

### What exactly "arms" it, and how is that scoped

The precise mechanism differs by browser and by which of two layers is asked about:

- **The gesture-detection layer** ("user activation," standardized by WHATWG). An activation-triggering input event is a *trusted* `keydown` (excluding Esc/reserved shortcuts/Caps Lock/Num Lock/Print Screen), `mousedown`, `pointerdown` (mouse), `pointerup` (non-mouse pointer), or `touchend`. (Source: https://developer.mozilla.org/en-US/docs/Web/Security/User_activation) This produces "sticky activation" — a boolean the Window keeps once triggered, that (unlike "transient activation," which is short-lived and gets consumed by APIs like `Window.open()`) does not get consumed by using it, and gates autoplay along with a handful of other APIs (`Navigator.vibrate()`, the `beforeunload` event). (Source: https://developer.mozilla.org/en-US/docs/Web/Security/User_activation)
- **The engagement-history layer** (Chrome-specific, MEI). Independent of any specific gesture in the current session, Chrome separately tracks a per-origin Media Engagement Index — "a ratio of visits to significant media playback events per origin" — stored per Chrome profile, and once a site's MEI crosses Chrome's threshold, Chrome autoplays sound-on media on that origin **without requiring a fresh gesture at all**. (Source: https://developer.chrome.com/blog/autoplay/, https://developer.chrome.com/blog/web-audio-autoplay)

### Does the armed state survive a reload? A new tab?

This is where the two layers give different answers, and where the primary sources are least precise:

- **MEI (Chrome only):** persists across reload and across new tabs, because it is stored per-origin per-profile, not per-tab or per-page-load. (Source: https://developer.chrome.com/blog/web-audio-autoplay) Chromium's own page adds that if a user opens a link in a new tab via the context menu, "the user gesture will be counted and the MEI will reflect any views on the new tab" — i.e., gestures in a new tab still feed the same per-origin MEI score. (Source: https://www.chromium.org/audio-video/autoplay/)
- **Sticky user activation (the gesture-based unlock, not MEI):** the WHATWG HTML Standard states this directly as a property of `Window`: "For the purpose of tracking user activation, each Window W has two relevant values: A last activation timestamp..." and "The last activation timestamp and last history-action activation timestamp are retained even after the Document changes its fully active status (e.g., after navigating away from a Document, or navigating to a cached Document). This means sticky activation state spans multiple navigations as long as the same Document gets reused." (Source: https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation) Read closely, that clause is about a Document being restored from the back/forward cache (bfcache) while its `Window` is reused — not about an ordinary reload. An ordinary reload replaces the page's `Document` with a fresh one; the spec text fetched here does not state outright whether the *same* `Window` object (and therefore the same last-activation-timestamp) is reused across an in-place reload or replaced along with the Document, so the reload question is not fully closed by this quote either — see Gaps. Chromium's own autoplay page separately adds a Chrome-specific, looser rule on top of spec-level activation: "The user interaction requirement only applies to contiguous navigations" — implying a gesture on one page can carry through a same-origin navigation chain, but not to a later, non-contiguous visit to the same site (e.g., closing the tab and coming back another day), unless MEI has separately been earned by then. (Source: https://www.chromium.org/audio-video/autoplay/) These are two distinct mechanisms — spec-level sticky activation, and Chrome's own "contiguous navigations" autoplay-specific carry-over rule — and it is not established from the sources fetched here that they behave identically for a simple reload. **A new tab is a new `Window`/browsing context**, so a gesture made in tab A does not, by itself, arm the sticky-activation layer of a *different, unrelated* tab B on the same origin — MEI is what is documented to carry across tabs on Chrome (see above), not sticky activation.

**Practical takeaway for the desk page (Chrome/Edge):** because the desk tab is opened once and stays open all day (the exact scenario in this ticket), a single click anywhere on the page early in the session (opening a thread, clicking a filter, anything but a scroll) is very likely enough to permit a later poll-triggered `Audio.play()`/`AudioContext.start()` with sound, for the remaining life of *that tab*, without needing a fresh click each time. What is not confirmed by a primary source is precisely whether a manual page **reload** of that same tab resets the sticky-activation bit (as opposed to the separate, definitely-persistent MEI mechanism) — this is called out in Gaps below. Firefox and Safari are more strictly per-gesture ("any use of audio/video requires a user gesture" per WebKit; "the user has interacted with the site" per Mozilla, plus Firefox's `media.block-autoplay-until-in-foreground` pref above), with neither vendor's fetched page describing an MEI-equivalent long-lived allowlist mechanism as clearly as Chrome's.

## 2. Badge

### Title/favicon while backgrounded

Changing `document.title` or a `<link rel="icon">` href from JavaScript while a tab is in the background is ordinary DOM manipulation with no special permission gate — MDN's Page Visibility API page, which is specifically about what a page can and cannot do while hidden, describes throttling of `requestAnimationFrame()` callbacks and of `setTimeout`/`setInterval` timers, but does not describe any restriction on DOM/title/favicon mutation while a page is hidden. (Source: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) No primary source was found stating a restriction exists; this is treated as "no restriction found," not as a spec that explicitly guarantees it (see Gaps).

### The Badging API (`navigator.setAppBadge` / `clearAppBadge`)

**Requires an installed app — not a normal tab.** The W3C/WICG Badging API spec is explicit that the API is scoped to "installed web applications": "an installed web application has an associated badge," and "user agents that never display application badges SHOULD NOT include `NavigatorBadge`." (Source: https://w3c.github.io/badging/) Chrome's own developer docs confirm this in practice: "To use the App Badging API, your web app needs to meet Chrome's installability criteria, and users must add it to their home screens" — an ordinary, non-installed browser tab does not get a working badge. (Source: https://developer.chrome.com/docs/capabilities/web-apis/badging-api) MDN's PWA how-to page states the same: "App badges are only supported when a PWA is installed on its host operating system. Badges appear on the app icon which only exists after the app has been installed." (Source: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/How_to/Display_badge_on_app_icon)

**Browser support, per MDN's own PWA badge page:**

| Browser | Support |
|---|---|
| Chrome (Windows, macOS), Edge (Windows, macOS) | Supported, installed PWA only |
| Chrome (Linux) | API present, but the badge is not actually displayed |
| Chrome/Edge on Android | Not supported — Android instead auto-badges the installed PWA's icon whenever there's an unread notification, independent of this API |
| Safari on iOS/iPadOS (16.4+) | Supported, requires notification permission to be granted |
| Firefox (any platform), Safari on macOS | Not supported |

(Source: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/How_to/Display_badge_on_app_icon) Chrome's own docs additionally note desktop support is Windows/macOS only, with ChromeOS support "in development" as of that page, and recommend feature-detecting rather than gating on install state: "you shouldn't make calls to the Badging API dependent on the install state. Just call the API when it exists." (Source: https://developer.chrome.com/docs/capabilities/web-apis/badging-api)

**Bottom line for this ticket:** since the desk page is described as an ordinary desktop browser tab (not installed as a PWA), `setAppBadge`/`clearAppBadge` would not do anything useful today on any of the four target browsers — it only ever affects an installed app's OS-level icon. The only unread-count signal available to a plain background tab is self-rolled: changing `document.title` (e.g., prefixing it with an unread count) and/or swapping the favicon image, which is unrestricted ordinary DOM work, not gated by the Badging API or any spec found in this research.

## 3. Background tab throttling

### Timers: `setTimeout`/`setInterval`

**Chrome (88+, tightened in 109).** Chrome throttles background-tab timers in three tiers. Chrome's own blog on Chrome 88's change: minimal/no throttling while a page is visible, playing sound, or otherwise active; a middle "throttled" tier once a page is hidden, checking timers roughly once per second; and, once **all** of the following are true, "**intensive throttling**": the page has been hidden for more than 5 minutes, the timer chain count is 5 or greater, the page has been silent for at least 30 seconds, and WebRTC is not in use — under intensive throttling, "the browser will check timers in this group once per minute." (Source: https://developer.chrome.com/blog/timer-throttling-in-chrome-88/) MDN's `setTimeout` page corroborates the same three-tier model for Chrome (minimal / throttled-to-1s / intensively-throttled-to-1-per-minute after 88), citing the identical four conditions. (Source: https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout)

**This 5-minute onset has since been shortened for pages that were already fully loaded before being backgrounded — but to 1 minute, not the 10 seconds originally proposed.** Chromium's "Intent to Ship: Quick intensive timer throttling of loaded background pages" thread opened with a proposal to "Enter Intensive Wake Up Throttling after 10 seconds if the page is fully loaded when it becomes hidden." The API owners did not approve that figure: "we achieved consensus that if you were content with 1 minute instead of 10 seconds, we'd be prepared to LGTM. For 10 seconds, we have additional concerns that would require more discussion and caveats." The feature's own author accepted this: "I agree that using a 1 minute grace period (instead of 10 seconds) is less risky... We'll experiment with this new grace period." The subsequent status update in the same thread confirms this 1-minute version is what was actually trialed and shipped: "The experiment has been running on 50% of stable for 4 weeks... I already have your LGTM to enable this by default. I'll flip the switch next Monday" — with LGTMs recorded shortly after this exchange, and no later message in the thread reverting to the original 10-second figure. (Source: https://groups.google.com/a/chromium.org/g/blink-dev/c/5SZB2CFFGqE) In practice, this means a desk tab that finished loading before being pushed to the background (the normal case — the tab was open and in use, then the staff member switched away) hits intensive throttling — the once-per-minute timer check — after about **1 minute** hidden, not 5 minutes, as long as the chain-count/silence/no-WebRTC conditions are also met (which a repeating poll satisfies well within that first minute). The 5-minute figure from the Chrome 88 post remains the documented condition for a page that is *still loading* when it is backgrounded; it is not the effective number for an already-open, already-loaded tab like the desk page. **Caveat:** the exact shipped grace-period value is reconstructed here from a mailing-list discussion thread, not from a developer.chrome.com/web.dev/MDN page stating "1 minute" as settled documentation — no such page was found in this research pass — so treat the "1 minute" figure as best-evidenced-from-primary-source rather than as certain as the other numbers in this document; see Gaps.

**Firefox.** MDN's `setTimeout` page states Firefox clamps timers in inactive tabs to a **minimum of 1 second (1000ms)**, with an exception: a tab that contains a running `AudioContext` is not throttled. (Source: https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout) MDN's Page Visibility API page gives more granular Firefox numbers via a budget model: each background window gets its own time budget in milliseconds, capped between **+50 ms and −150 ms**; throttling only starts once a window has been hidden for **30 seconds**; the budget regenerates at **10 ms per second**, and a timer task only runs once its window's budget is non-negative. (Source: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

**Chrome, again — the budget model.** Chrome's own 2017 "Background Tabs in Chrome 57" post describes an earlier, separate budget mechanism (predating both the 2021 Chrome-88 intensive-throttling tier and the 2022/Chrome-109 quick-throttling change above): "A page is subjected to time budget limitations after 10 seconds in the background," and "the budget continuously regenerates with time (currently set to a rate of 0.01 seconds per second)," with timer execution permitted only while the per-page budget stays non-negative. (Source: https://developer.chrome.com/blog/background_tabs) MDN's Page Visibility API page describes the same budget shape for Chrome (seconds-denominated, ~10-second onset, 10ms/second regeneration) alongside Firefox's equivalent (milliseconds-denominated, +50ms/−150ms cap, 30-second onset, same 10ms/second regeneration). (Source: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) This older, finer-grained per-tab budget throttling and the newer, coarser "intensive throttling" tier (once-per-minute checks, now onset at roughly 1 minute for already-loaded pages per Chrome 109 above) are two separate, stacked mechanisms Chrome has layered in over several releases, not one single number.

**Exemptions (both Firefox and Chrome, per the same MDN page):** a tab playing audio is treated as foreground and not throttled; a tab with an active real-time network connection — the page names **WebSockets and WebRTC** specifically — goes unthrottled "in order to avoid closing these connections timing out and getting unexpectedly closed"; and IndexedDB transactions are left unthrottled to avoid timeouts. (Source: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) **EventSource/SSE is not named in this exemption list one way or the other** — see Gaps.

**Safari/WebKit.** WebKit's own blog confirms timers are throttled in background tabs, but gives no specific numbers: "Timers are throttled" is listed among WebKit's automatic power-saving steps for inactive pages, alongside suspending CSS/SVG animations. (Source: https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/) On macOS, this is implemented via **App Nap** — "the web process for a tab that is not visually updating gets lower priority and has its timers throttled" — while on iOS, "tabs are completely suspended when possible," a stricter behavior than macOS's App Nap. (Source: https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/) The same post is explicit that pages can still wake the CPU: "pages can trigger CPU wake-ups via timers (`setTimeout` and `setInterval`), messages, network events, etc.," and recommends developers proactively reduce work via the Page Visibility API rather than rely on WebKit's own throttling alone. No numeric clamp (a "1 second minimum" equivalent to Firefox's, or a specific per-minute rule equivalent to Chrome's) was found on any WebKit/Apple primary page fetched in this research — see Gaps.

**Edge.** As Chromium-based, Edge is expected to inherit Chrome's timer-throttling behavior; no Edge-specific documentation of its own timer-throttling numbers was found (mirroring the same gap noted for Edge's autoplay policy above) — treated as inherited-but-not-independently-documented, not confirmed by a Microsoft primary source.

### Does an open EventSource (SSE) keep receiving messages while backgrounded?

MDN's dedicated Server-Sent Events pages (both the API reference and the "Using server-sent events" guide) do not discuss background-tab behavior at all — no statement either confirming or denying that message delivery continues, is delayed, or is exempted from throttling while the tab is hidden. (Source: https://developer.mozilla.org/en-US/docs/Web/API/EventSource, https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) The one relevant thing a primary source does say is the exemption list above: **WebSockets and WebRTC** are named explicitly as unthrottled real-time connections; **EventSource is not named**, in either direction. (Source: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) Mechanically, the throttling described everywhere above is specifically throttling of **timer callback execution** (`setTimeout`/`setInterval` tasks) — an open SSE connection's `message` event is delivered by the browser's network stack when bytes arrive on an already-open connection, not by a polled timer, so the named timer-throttling rules do not mechanically apply to it the way they apply to a `setInterval` poll loop. That reasoning is not, however, a claim any fetched primary source makes explicitly about EventSource by name — it is inferred from how the two mechanisms work, not confirmed as documented EventSource-specific behavior. This gap is significant enough that it is called out again below rather than treated as settled.

### Worked worst-case delay: message sent at 14:00:00 while the desk tab is backgrounded

**Assumptions used:** the desk tab has already been in the background (hidden — MDN's Page Visibility API page defines `hidden` explicitly as covering both cases: "The page's content is not visible to the user, either due to the document's tab being in the background or part of a window that is minimized, or because the device's screen is off," so the same throttling numbers below apply whether the desk tab is behind other tabs or the whole browser window is minimized. (Source: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)) for well over the throttling onset by 14:00:00 — realistic for "a tab open all day, often behind other tabs" — and is not currently playing audio or holding a WebRTC connection, so Chrome's intensive-throttling conditions are met. Because the desk tab is fully loaded long before being backgrounded (the normal case for a tab that's been open and in use all day), the applicable onset is Chrome 109's shipped-as-negotiated **~1-minute** "quick intensive throttling of loaded background pages" rule (see caveat above on how this figure was reconstructed), not the older 5-minute figure from the Chrome-88 post — 1 minute hidden is a near-certainty by the time any poll response matters for a tab open all day, and the chain-count-≥5 condition is met well within the first few minutes of a repeating 10-second poll.

**(a) `setInterval` poll every 10 seconds, Chrome/Edge:** Once intensively throttled — which, per the above, applies to the desk tab after roughly 1 minute of being backgrounded, not 5 minutes — Chrome checks timers in the throttled group **once per minute**, batching multiple due timers to fire together at that checkpoint, regardless of their individual requested intervals. (Source: https://developer.chrome.com/blog/timer-throttling-in-chrome-88/) Because the per-minute checkpoint's alignment relative to wall-clock time is not tied to when the server happens to send a message, the worst case is that the checkpoint has *just* fired an instant before 14:00:00, meaning the poll doesn't get its next chance to run until just under 60 seconds later. **Worst-case delay: up to ~1 minute (just under 60 seconds).** This is markedly worse than the nominal 10-second poll interval would suggest, and — given how quickly (roughly 1 minute hidden, not 5 minutes) a long-open desk tab qualifies for it — it is the realistic case for this ticket's scenario, not an edge case.

For Firefox, the documented mechanism is a budget-drain model rather than a fixed "once per minute," with a much smaller cap (max budget +50ms, min −150ms, regenerating 10ms/second, throttling active after 30s hidden) (Source: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) and a separate, simpler statement on the `setTimeout` page that inactive-tab timers are clamped to a 1-second minimum (Source: https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout). Neither of Firefox's own documented numbers describes anything close to Chrome's per-minute batching; a 10-second poll on Firefox, per these figures, should fire close to its nominal 10-second cadence, with only single-digit-second jitter from the budget mechanism, not a full extra minute of delay. This is a real, documented difference between Chrome/Edge and Firefox's throttling depth for a poll-based desk page.

No numeric worst-case can be computed for Safari from the fetched primary source, since WebKit's own blog states timers are throttled via App Nap but gives no specific clamp value or checkpoint interval (Source: https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/) — see Gaps.

**(b) Open SSE stream:** If EventSource message delivery is, as reasoned above, driven by the network stack rather than gated by the timer-throttling mechanisms documented for Chrome/Firefox/WebKit, the worst-case delay would be dominated by ordinary network/event-loop latency (sub-second), not by the minute-scale throttling in (a) — matching the treatment WebSockets explicitly receive per MDN's Page Visibility API page. However, since no primary source names EventSource in that exemption (only WebSockets and WebRTC are named), this conclusion is a reasoned inference, not a documented fact, and is repeated in Gaps below as something this research could not close out with a citation.

## 4. Vercel: maximum duration of a streaming response

Vercel's Functions duration docs, fetched directly and current as of this research pass (page `last_updated: 2026-08-24`), give the following for Fluid Compute (on by default since April 23, 2025):

| Plan | Default duration | Maximum duration | Extended maximum |
| --- | --- | --- | --- |
| Hobby | 300s (5 min) | 300s (5 min) | not available |
| Pro | 300s (5 min) | **800s** | **1800s (30 min), Beta** |
| Enterprise | 300s (5 min) | 800s | 1800s (30 min), Beta |

(Source: https://vercel.com/docs/functions/configuring-functions/duration, https://vercel.com/docs/fluid-compute)

This matches, and as of this research pass confirms still current, the table already found in prior research at `research/buy-or-build-chat:docs/research/buy-or-build-chat.md` (that prior note also already treated 800s as Pro/Enterprise's plain maximum, with only the 1800s tier marked beta). Vercel's current docs state plainly that "**the 800 second maximum is generally available for Pro and Enterprise teams**" (Source: https://vercel.com/docs/functions/configuring-functions/duration) — confirming 800s is a settled, non-beta figure, while the 1800s (30-minute) tier remains "Beta." The 1800s extended tier requires setting `maxDuration` per-function (in code or `vercel.json`), is not available as a project-level default, and is limited to specific runtimes: `nodejs20.x`/`22.x`/`24.x`, Bun `1.x`/`1.4.x`, and `python3.12`–`3.14`. It is also incompatible with Secure Compute / Static IPs during the beta. (Source: https://vercel.com/docs/functions/configuring-functions/duration)

A relevant operational note for a long-lived streaming response: "For long-running request handlers that keep a client connection open over HTTP/2, Vercel sends connection-level HTTP/2 `PING` frames while the response is idle. HTTP/1.1 does not have an equivalent protocol frame, so HTTP/1.1 clients and intermediate network layers may still close idle connections. For those cases, stream progress or heartbeat data while work is running." (Source: https://vercel.com/docs/functions/configuring-functions/duration) This means an SSE stream on Vercel should not assume the platform alone keeps an idle-but-open HTTP/1.1 connection alive — sending periodic heartbeat/comment lines is documented as the mitigation. This determines the maximum sensible gap between forced reconnects for an SSE stream on this stack: at most 800 seconds (~13.3 minutes) by default configuration on Pro without opting into the beta, or up to 1800 seconds (30 minutes) per-function if the extended-duration beta is deliberately configured — whichever the app chooses to set as `maxDuration`, the stream must reconnect at or before that ceiling, plus send heartbeats to avoid idle-connection closure by intermediate network layers on HTTP/1.1.

## Gaps

- **Whether Chrome/Edge's spec-level "sticky activation" (as opposed to the separately-persistent MEI mechanism, and as opposed to Chrome's own looser "contiguous navigations" autoplay rule) survives a manual page reload of the same tab.** The WHATWG HTML Standard ties the last-activation-timestamp to `Window` and states it is "retained even after the Document changes its fully active status (e.g., after navigating away from a Document, or navigating to a cached Document)" (Source: https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation) — but on inspection this clause is about bfcache restoration of a Document within a reused Window, not explicitly about an ordinary reload replacing the Document outright. Whether the same `Window` object (and its timestamp) is reused across an in-place reload is not stated in the spec text fetched here. Chrome's own "contiguous navigations" autoplay rule (https://www.chromium.org/audio-video/autoplay/) is a separate, Chrome-specific mechanism layered on top and may be more permissive than spec-level sticky activation for a reload — neither source resolves "does F5 reset it" with a direct quote.
- **Whether Firefox and Safari have a Chrome-MEI-equivalent long-lived, per-origin autoplay allowlist that survives reload/new-tab without a fresh gesture.** MDN's autoplay guide and WebKit's autoplay blog both describe a per-gesture requirement but neither page fetched in this research documents an engagement-history mechanism comparable to Chrome's MEI; this may mean no such mechanism exists on those browsers, or may simply mean it wasn't covered in the pages fetched. Not confirmed either way from a primary source.
- **Whether Firefox's `media.block-autoplay-until-in-foreground` (default `true`) re-blocks a poll-triggered sound in a tab that was foregrounded earlier in the session and is now backgrounded again, or only blocks audio that is asked to autoplay while the tab has never yet been foreground.** MDN's autoplay guide states the preference's purpose (stopping a tab the user can't find from starting to play sound) but does not spell out this specific edge case. (Source: https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay) If it does re-block, Firefox may be the one browser of the four where a backgrounded desk tab cannot reliably play an alert sound at all, regardless of an earlier gesture — this would be a materially important fact for AND-83 and is worth confirming with direct testing before relying on Firefox for audio alerts.
- **The exact grace period for Chrome's "quick intensive throttling of loaded background pages" (Chrome 109) is reconstructed from a mailing-list discussion, not a settled docs page.** The original Nov 2022 proposal asked for a 10-second grace period; the Blink API owners only approved 1 minute, the feature's author agreed to ship with 1 minute, and a later status update in the same thread describes a 4-week, 50%-of-stable experiment before enabling by default — consistent with, but not an explicit, single-sentence restatement of, "1 minute" as the final shipped number. (Source: https://groups.google.com/a/chromium.org/g/blink-dev/c/5SZB2CFFGqE) No developer.chrome.com, web.dev, or MDN page was found stating this specific grace period as settled documentation. Treat "~1 minute" as well-evidenced but not as certain as the other figures in this document, and verify directly (e.g., a throttling test page) before relying on it for a production timing budget.
- **Exact numeric timer-throttling clamp for Safari/WebKit** (a number comparable to Firefox's 1-second clamp or Chrome's "once per minute" intensive-throttling rule). WebKit's own power-usage blog post states timers are throttled via App Nap but gives no specific interval or budget figure. No other WebKit/Apple primary page with a specific number was found in this research pass.
- **Whether an open EventSource/SSE connection is exempt from background-tab timer throttling the same way WebSockets and WebRTC are.** MDN's Page Visibility API page names WebSockets and WebRTC explicitly as unthrottled real-time connections but does not mention EventSource in either direction, and neither of MDN's own EventSource-specific pages discusses background-tab behavior at all. Section 3's worked answer for the SSE case is therefore a reasoned inference from how the underlying mechanisms work (network-driven delivery vs. timer-driven polling), not a documented fact — this is the single largest open question in this research, since it directly affects whether SSE has a real latency advantage over polling in a backgrounded tab.
- **Edge-specific throttling and autoplay documentation.** No Microsoft-authored page was found describing Edge's own timer-throttling numbers or a from-Chrome-diverging autoplay mechanism; both are treated as "inherited from Chromium, not independently confirmed by a Microsoft primary source," based on Edge's own admin-policy docs pointing at the same Allow/Limit model Chrome uses, without adding Edge-specific detail.
- **Whether changing `document.title` or the favicon while backgrounded is explicitly guaranteed (rather than merely undocumented-as-restricted).** No primary source was found stating outright "a hidden page may always update its title/favicon" — the conclusion in Section 2 rests on the absence of any stated restriction in MDN's Page Visibility API page, which is a different, weaker kind of evidence than an explicit confirmation.
