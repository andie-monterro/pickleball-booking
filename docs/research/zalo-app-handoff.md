# Zalo in-app webview: app-to-app hand-off (ride apps)

Research pass conducted 2026-09-10.

## Scope and relationship to prior research

This document extends [AND-90](https://linear.app/andie-monterro/issue/AND-90/find-out-what-the-app-can-do-inside-zalos-in-app-browser-and-what-a) (`docs/research/zalo-webview-and-push.md`, branch `research/zalo-webview-and-push`, pushed `31cd17d`). AND-90 covered WebRTC, service workers, and web push inside Zalo's **plain** in-app browser — the webview Zalo opens for an ordinary `https://` link a Player taps in a chat, as opposed to the separate **Zalo Mini App** platform, which has its own SDK and JS bridge. AND-90's own gap list left one item open that this ticket exists to close:

> "Whether any programmatic hand-off from a web page to the system browser is possible from inside Zalo's webview (universal links, `intent://` URLs, `window.open` targeting `_system`, or a Zalo-specific JS bridge call) is undocumented." (AND-90, gap 8)

AND-90 also found one directly relevant, still-unresolved thread: a Zalo developer-community post titled "Không thể chuyển hướng tới app momo từ zalo webview" ("Cannot redirect to the Momo app from Zalo's webview"), whose body could not be retrieved because Zalo's community site is a client-rendered SPA that returns only a page `<title>` to automated fetching. That same resistance was hit again in this pass (see Q2 and Gaps).

The scope here is the same **plain in-app browser**, not Mini Apps. Where Mini-App-specific material surfaced, it is labeled as such and kept separate, following AND-90's convention.

The following facts are taken as already established in `docs/research/zalo-webview-and-push.md` and are not re-derived here:
- Zalo's iOS in-app browser is necessarily a WKWebView instance (App Store guideline 2.5.6 requires WebKit).
- Zalo's Android in-app browser is Android's system WebView (Chromium-based); the Chromium build number is a property of the device, not something Zalo version-locks.
- A page can detect it is running inside Zalo via a `Zalo iOS/…` / `Zalo android/…` token appended to the User-Agent string, per a crowd-sourced UA-string database (not Zalo's own documentation).

## Q1. App-to-app launching from a webview: Android and iOS platform behavior

The ticket asks for a three-way distinction per mechanism: **opens the other app**, **silently dropped**, or **depends on the host app's own configuration**. That distinction turns out to be the entire answer — and it has opposite defaults on the two platforms.

### Android (system WebView, as embedded by a host app such as Zalo)

**Custom URL scheme (`grab://…`) — depends on host app configuration, defaulting toward "dropped."**
- Android's own WebView guide states the *un-embedded* default plainly: "When the user taps a link from a web page in your `WebView`, by default, Android launches an app that handles URLs. Usually, the default web browser opens and loads the destination URL." But it immediately explains why a host app that wants an in-app browsing experience — which is the entire point of Zalo's feature — cannot leave that default in place: "To open links tapped by the user, provide a `WebViewClient`… All links the user taps load in your `WebView`." (Source, primary, Android developer docs: https://developer.android.com/guide/webapps/webview)
- The same page warns that "`WebView` applies restrictions when requesting resources and resolving links that use a custom URL scheme," and that a malformed or non-http custom scheme may not even reach `shouldOverrideUrlLoading()`. (Same source.)
- Google's own AdMob click-behavior documentation is explicit about the consequence: "`WebView` doesn't support custom URL schemes which could be returned in ads if the click destination is to a separate app," and instructs the host app to intercept the scheme itself in `shouldOverrideUrlLoading()`. (Source, primary, Google: https://developers.google.com/admob/android/browser/webview/click-behavior)
- Numerous independent developer reports converge on what happens if a host app naively fires `startActivity()` for a scheme with no registered handler: `ActivityNotFoundException`, uncaught unless the host app wraps the call in a try/catch. (Source, secondary/informal, Stack Overflow: https://stackoverflow.com/questions/35609107/android-open-intent-protocol-in-webview, https://stackoverflow.com/questions/27522003/android-redirect-to-a-url-with-my-custom-scheme-doesnt-work)
- **Net: a custom scheme is silently dropped or crashes inside Zalo's webview unless Zalo's `WebViewClient.shouldOverrideUrlLoading()` explicitly detects the scheme and calls `startActivity()` itself.** Zalo must have *some* `WebViewClient` (an in-app browser cannot function without one), but nothing found shows it does the additional, scheme-specific interception step.

**`intent://` URL — depends on host app configuration; this is Chrome's own feature, not a WebView platform primitive.**
- Chrome's documentation defines the `intent://` convention and its syntax ("`intent: HOST/URI-path #Intent; package=[string]; …; end;`"), and notes the accompanying `S.browser_fallback_url` extra: "When a fallback URL is specified… Chrome removes `browser_fallback_url` so the target app doesn't see this value." It also documents when Chrome itself declines to launch an external app: "The intent cannot be resolved… A JavaScript timer tried to open an application without a user gesture." (Source, primary, Chrome developer docs: https://developer.chrome.com/docs/multidevice/android/intents)
- This parsing and fallback logic lives in Chrome's own code, not in the generic `android.webkit.WebView`/`WebViewClient` class. A consistent, independently-repeated pattern across many developer answers confirms that a raw embedded `WebView` does not understand `intent://` at all — it throws `net::ERR_UNKNOWN_URL_SCHEME` or an `ActivityNotFoundException` unless the host app manually parses the URI with `Intent.parseUri(url, Intent.URI_INTENT_SCHEME)` inside `shouldOverrideUrlLoading()` and replicates Chrome's resolve/fallback logic itself. (Source, secondary/informal, convergent across multiple Stack Overflow threads: https://stackoverflow.com/questions/33151246/how-to-handle-intent-on-a-webview-url, https://stackoverflow.com/questions/35609107/android-open-intent-protocol-in-webview)
- **Net: silently dropped (error page, or a crash the host app must catch) unless Zalo has independently re-implemented Chrome's `intent://` convention inside its own `WebViewClient`.** No evidence either way was found for Zalo specifically.

**Universal/App Link (an `https://` URL the target app has registered and verified) — depends on host app configuration, but degrades safely.**
- Android App Links resolution (Digital Asset Links `assetlinks.json`, `android:autoVerify="true"`) is a system-level `PackageManager`/`Intent`-resolution mechanism that determines which app is the default handler for a verified domain. (Source, primary, Android developer docs: https://developer.android.com/training/app-links/verify-android-applinks)
- Whether a navigation *inside an embedded WebView* is even offered to that OS-level resolution step, rather than simply being loaded in place as an ordinary HTTP request, is controlled by the host's `WebViewClient`. A secondary source comparing embedding strategies states the practical split plainly: "Android Custom Tabs (used by some apps) do support App Links interception in most cases. But raw WebViews (used by others) do not." (Source, secondary/informal: https://linkrunner.io/blog/universal-links-app-links-break-in-app-browsers)
- **Net: most likely loads as an ordinary web page inside Zalo's webview — a safe, non-broken fallback — unless Zalo specifically hands the navigation off to Android Custom Tabs or re-resolves it via `PackageManager` itself.** This is a materially different, gentler failure mode than the custom-scheme and `intent://` cases above.

### iOS (WKWebView)

**Custom URL scheme — depends on host app configuration.**
- WKWebView does not natively navigate non-http(s) schemes. The containing app's `WKNavigationDelegate` must detect the scheme in its navigation-policy callback, cancel the WebView's own navigation, and call `UIApplication.shared.open(url)` itself for the app switch to happen. This is standard, universally documented iOS webview-integration practice; we could not fetch Apple's `WKNavigationDelegate` decidePolicy reference page directly during this pass (it did not resolve to full body content), so the mechanism is corroborated here via Apple's `open(_:options:completionHandler:)` documentation instead: "If the specified URL scheme is handled by another app, iOS launches that app and passes the URL to it… If no app is capable of handling the specified scheme, the completion handler is called with the success parameter set to false." (Source, primary, Apple developer docs: https://developer.apple.com/documentation/uikit/uiapplication/open(_:options:completionhandler:))
- **Net: silently dropped unless Zalo's `WKNavigationDelegate` explicitly intercepts the scheme and calls `UIApplication.shared.open()`.** No evidence either way was found for Zalo specifically.

**`intent://` — not applicable.** This is an Android-only, Chrome-specific convention.

**Universal Link — opens the app by default, per Apple's own documentation; this reverses the assumption behind the ticket's framing.**
Apple's current documentation is explicit that Universal Links are honored from inside an embedded WKWebView, not only from Safari:

> "With universal links, users open your app when they click links to your website within their browser app and WKWebView, and when they click links that result in a call to: `UIApplication.open(_:options:completionHandler:)`…" (Source, primary, Apple, current: https://developer.apple.com/documentation/xcode/allowing-apps-and-websites-to-link-to-your-content)

Apple's older (2016) but still-published archived App Search Programming Guide states the same point even more directly, including the specific case this ticket asks about — a link tapped inside a third-party app's own embedded webview:

> "If you instantiate a `SFSafariViewController`, `WKWebView`, or `UIWebView` object to handle a universal link, iOS opens your website in Safari instead of opening your app. However, if the user taps a universal link from within an embedded `SFSafariViewController`, `WKWebView`, or `UIWebView` object, iOS opens your app." (Source, primary but archived, Apple: https://developer.apple.com/library/archive/documentation/General/Conceptual/AppSearch/UniversalLinks.html)

A secondary but well-corroborated source (a highly-cited Stack Overflow answer quoting the same Apple text) draws out the practical reading for exactly this scenario — a host app's embedded WKWebView linking out to a *different* app's Universal Link domain: "the OS will behave normally: it will open your app, respecting Universal Link rules." (Source, secondary/informal: https://stackoverflow.com/questions/34816577/when-can-i-use-a-sfsafariviewcontroller-wkwebview-or-uiwebview-with-universal)

The only two documented carve-outs found do not apply to this scenario: (1) an app calling `open()`/`openURL` on its *own* registered Universal Link domain does not get routed back into itself — irrelevant, since Zalo is not opening its own domain; (2) the "already in Safari, same domain" rule that keeps a user in Safari rather than re-opening the app — irrelevant here since this is Zalo's own embedded webview, not Safari, and the ride app's domain differs from the booking site's domain.

There is, however, a documented (informal, undocumented-by-Apple) technique by which a host app can actively **suppress** Universal Link interception inside its own WKWebView: returning a `WKNavigationActionPolicy` with the raw value `.allow.rawValue + 2` from the navigation-policy delegate method forces the navigation to behave as a plain web link instead of triggering Universal Link resolution. This is discussed by iOS developers as the mechanism apps like Instagram and LinkedIn reportedly use to keep users inside their own in-app browsers. (Source, secondary/informal: https://darcy.org/blog/ios-disable-universal-links/, https://www.appsloveworld.com/swift/100/33/stop-wkwebview-redirecting-to-another-app-based-on-universal-link; corroborated in general terms by https://linkrunner.io/blog/universal-links-app-links-break-in-app-browsers, which describes major in-app browsers blocking Universal Link interception on initial page load.)

**Net: on iOS, a Universal Link opens the target app by default, per Apple's own current and archived documentation — the opposite polarity from Android's default. The open question is not "does the platform support this" but "has Zalo deliberately turned it off," which only a real-device test can answer (see Gaps).**

### Net for Q1

The two platforms default in opposite directions. Android's default (once any `WebViewClient` exists, which an in-app browser must have) is to keep everything inside the webview unless the host app explicitly intercepts a navigation and hands it to another app — so all three mechanisms are "depends on host configuration," biased toward silent drop for custom schemes and `intent://`, and toward a safe web-page fallback for Universal/App Links. iOS's documented default is the reverse for Universal Links specifically: they fire by default from inside an embedded WKWebView, and it takes deliberate host-app code to suppress that. Custom URL schemes remain host-dependent on both platforms.

| Mechanism | Android (WebView) | iOS (WKWebView) |
|---|---|---|
| Custom scheme (`grab://…`) | Depends on host; default is dropped/crash if unhandled | Depends on host; default is dropped (silent `open()` failure) if unhandled |
| `intent://` | Depends on host re-implementing Chrome's own convention; default is dropped/crash | N/A (Android-only) |
| Universal/App Link | Depends on host; default degrades safely to loading as a web page | Opens the app **by default** per Apple docs, unless the host suppresses it |

(Source, secondary/informal but from an official "Supporter" role on Zalo's own Mini App community: https://miniapp.zaloplatforms.com/community/2840689375930558144/zalo-mobile-redirect-tu-webview-cua-zalo-sang-browser)

A second, partially relevant and equally unreachable thread ("Android không tự đóng Webview khi redirect từ bên ngoài về Miniapp") has a search-summarized gist suggesting that, in a *Mini App payment* flow, redirecting from Zalo's webview to the Momo app and back succeeded on at least one occasion, with a platform difference in whether the webview auto-closes afterward. This would imply outbound app-switching does work in some Zalo-mediated context — but it is a different context (a payment webview inside a Mini App, likely using Zalo's Mini App SDK) from the plain in-app browser this ticket is about, and its body is unread. (Source, secondary/unverified: https://miniapp.zaloplatforms.com/community/8531637315294035402/android-khong-tu-dong-webview-khi-redirect-tu-ben-ngoai-ve-miniapp)

Targeted Vietnamese-language searches (Tinhte.vn, Voz.vn, Vietnamese Stack Overflow, Reddit) specifically for Grab, Be, or Xanh SM deep links failing or succeeding from inside Zalo's plain webview returned nothing on-topic — only unrelated Zalo-Momo money-transfer tutorial content. If Grab and/or Be also have Zalo Mini Apps, a booking page could in principle route a Player through a Zalo-internal Mini App deep link instead of attempting a native OS-level app hand-off — this is a different mechanism from anything Q1 covers, and is out of scope here (it belongs to whichever ticket surveys what each ride service actually permits, not this webview-behavior ticket).

This question **cannot be closed from documentation** — see the real-device tests in Gaps.

## Q3. The fallback when the ride app is not installed

**Custom URL scheme, iOS.** `UIApplication.shared.open()` for an unregistered scheme calls its completion handler with `success = false`; the OS shows nothing to the user itself — a documented silent failure at the API level. (Source, primary, Apple: https://developer.apple.com/documentation/uikit/uiapplication/open(_:options:completionhandler:)) `canOpenURL(_:)` "returns false if the device doesn't have an installed app registered to handle the URL's scheme, or if you haven't declared the URL's scheme in your Info.plist file," and is capped at 50 calls per declared-scheme-list app (`LSApplicationQueriesSchemes`). That page is marked deprecated in Apple's current documentation (superseded by Universal Links guidance) but remains accurate and widely used for scheme checks. (Source, primary but flagged deprecated, Apple: https://developer.apple.com/documentation/uikit/uiapplication/canopenurl(_:)) None of this is reachable from a web page directly — `canOpenURL`/`open()`/`LSApplicationQueriesSchemes` are native APIs; only Zalo's own app code could invoke them on a page's behalf, and there is no evidence it does.

**Custom URL scheme, Android.** Firing `Intent.ACTION_VIEW` for an unregistered scheme via `startActivity()` throws `ActivityNotFoundException`; Android provides no automatic fallback, and the host app must catch the exception itself. Confirmed by consistent, independently-reproduced stack traces across multiple sources. (Source, secondary/informal, convergent: https://stackoverflow.com/questions/33151246/how-to-handle-intent-on-a-webview-url, https://github.com/facebook/react-native/issues/10055)

**`intent://`, Android.** The `S.browser_fallback_url` extra is **Chrome's own feature**, not an Android-platform or generic-WebView automatic behavior. Chrome's documentation confirms the fallback is something Chrome's own code path honors: "When a fallback URL is specified… Chrome removes `browser_fallback_url` so the target app doesn't see this value." (Source, primary, Chrome developer docs: https://developer.chrome.com/docs/multidevice/android/intents) Every working implementation found requires the host `WebViewClient` to parse the URI itself (`Intent.parseUri(url, Intent.URI_INTENT_SCHEME)`), check whether it resolves, and manually load the fallback URL if not — i.e., **this fallback only exists inside Zalo's webview if Zalo's own code reimplements it**, which is unconfirmed. (Source, secondary/informal, convergent across independent answers: https://stackoverflow.com/questions/33151246/how-to-handle-intent-on-a-webview-url, https://stackoverflow.com/questions/35609107/android-open-intent-protocol-in-webview)

**Universal/App Link, both platforms, app not installed.** Both platforms document a clean web-page fallback, independent of browser-vs-embedded-webview: on iOS, "If the person hasn't installed your app, the system opens the URL in their default web browser, allowing your website to handle it." (Source, primary, Apple: https://developer.apple.com/documentation/xcode/allowing-apps-and-websites-to-link-to-your-content) On Android, App Links resolution only takes over when a package passes Digital Asset Links verification; absent an installed, verified app, an `https://` navigation is just an ordinary web request. (Source, primary, Android developer docs: https://developer.android.com/training/app-links/verify-android-applinks)

**One precision the ticket's own framing invites, and that matters for the map:** "opens as a web page" here means the **ride app's own linked page** loads — not automatically a store page. A store-page fallback (e.g. via a smart-link/deferred-deep-link service) is something the *ride app's own URL* would have to implement on its side (redirecting an uninstalled visitor to Google Play / the App Store); it is not something the OS or the webview provides automatically for a plain `https://` link. Whether Grab, Be, or Xanh SM's own published links do this is outside this document's scope — it is a fact about what each ride service publishes, which belongs to the ride-service research ticket, not this one.

**And a second precision that matters for the map**: "loads as a web page" for a Universal/App Link is conditional on the navigation ever reaching the OS's app-resolution step at all — which, per Q1, is itself host-app-dependent on Android and (by Apple's default) automatic on iOS. So on Android specifically, the practical fallback for "app not installed" and the practical behavior for "app not offered a hand-off at all" converge on the same visible outcome (a web page loads) even though the underlying reason differs — from the Player's point of view they look identical, which is worth noting for question 4 below and for the map's UX framing.

### Summary table for "target app not installed"

| Mechanism | iOS | Android |
|---|---|---|
| Custom scheme | Silent failure (`open()` completion = false; no dialog shown) | `ActivityNotFoundException` (crash unless the host app catches it) |
| `intent://` | N/A | Falls back to `S.browser_fallback_url` only if the host app (Zalo) itself implements that Chrome-specific convention; otherwise crash/error |
| Universal/App Link | Loads the ride app's own linked page in the default browser — a store redirect only if that page itself implements one | Loads the ride app's own linked page — a store redirect only if that page itself implements one |

**Net for Q3: a silent failure is the realistic worst case for custom schemes and unhandled `intent://` links on both platforms — nothing visible happens, or a generic error page appears, with no path to the ride app or the store. A Universal/App Link degrades to a normal web page in the worst case, never to nothing, which makes it the safer mechanism to depend on regardless of which app is or isn't installed.**

## Q4. Detection

AND-90 established that a page can detect Zalo's plain in-app browser via a `Zalo iOS/…` / `Zalo android/…` token appended to the User-Agent string (a crowd-sourced observation, not Zalo's own documentation). This pass looked for reasons that detection could be unreliable.

- **No documented case of the token being absent** was found — no report of an older Zalo version, an alternate webview mode, or a Mini-App context omitting it. This is a **gap** (absence of evidence, not evidence of absence), not a confirmed guarantee that the token is always present.
- **False positives from an unrelated app or bot** are not documented anywhere, and the general pattern of an embedding app appending its own distinctive token (the same pattern Facebook's `FBAN` token follows) makes an accidental collision on the literal substring "Zalo" unlikely — but this is reasoned inference, not a documentation-backed guarantee. (Source, secondary/informal, general webview-detection pattern discussion, not Zalo-specific: https://github.com/nonwip/is-webview)
- **A concrete, narrower false-positive risk exists for server-side detection specifically, not for the client-side JS check this ticket is actually about.** Zalo runs a link-preview crawler that fetches a page when a Player merely pastes a link into a chat (to render the chat's preview card), separate from the human later opening it. A secondary source discussing a Zalo phishing exploit chain states this crawler "crawls the destination page with a special user agent," but the exact string was not found. If that crawler's UA also contains "Zalo," a server-side check keyed on the same substring could misfire on the preview fetch rather than the real visit. This does not affect a client-side `navigator.userAgent` check running in the Player's own browser tab, which only ever sees the Player's real session. (Source, secondary/informal: https://blog.vincss.net/ex008-the-exploit-chain-allows-to-take-control-of-zalo-user-accounts/) Flagged low-confidence; the exact crawler UA string is a gap.
- **UA spoofing** is technically always possible (any client can override `navigator.userAgent`), but in the realistic scenario — a Player tapping a shared link inside their own, genuine Zalo app — there is no plausible incentive or path for the string to have been altered. Treated as a low-severity theoretical caveat, consistent with how AND-90 treated the same point.
- **Chromium/Android WebView User-Agent Reduction is not expected to break the token, on current evidence, but this is reasoned rather than directly confirmed.** Google states the reduction targets the OS/device/build segment of the UA: "the default, reduced WebView User-Agent string will have the OS, CPU, and Build information reduced to the static 'Linux; Android 10; K' string, with minor/build/patch version information also reduced to '0.0.0'." (Source, primary, Android Developers blog: https://android-developers.googleblog.com/2024/12/user-agent-reduction-on-android-webview.html) A Chromium source patch confirms the same scoping: "This change enforces the platform string to be 'Linux; Android 10; K; wv' for all reduced WebView User-Agents, regardless of the underlying form factor." Zalo's own appended token (`Zalo android/… ZaloTheme/… ZaloLanguage/…`) sits architecturally after this reduced segment, in the part of the string Zalo's own app code appends, not the part Chromium rewrites — so reduction is unlikely to strip it. This conclusion is **inferred from how the reduction is scoped, not a direct Zalo statement**, and should be treated accordingly. User-Agent Client Hints, the longer-term replacement mechanism, is documented as applying only "for applications that send the default User-Agent string" — since Zalo customizes its UA, it likely falls outside that migration path for now, though again this is inference, not a Zalo-specific confirmation.

**Net for Q4: yes, with caveats.** The token-based check AND-90 found is the best available detection method and nothing found in this pass contradicts it. The realistic risks are theoretical (no documented absent-token case, no documented collision, spoofing requires an implausible actor) rather than live known failure modes. The one concrete adjacency — Zalo's link-preview crawler potentially sharing the same substring — matters only if detection is ever done server-side against raw request logs, not for a client-side JS check running in the Player's own tab, which is the only form of detection this map needs.

## Verdict

The ticket's own framing assumed Universal Links might be blocked from firing inside a third-party embedded webview on iOS. Apple's own current and archived documentation say the opposite: a Universal Link fires by default from inside an embedded WKWebView, and only a host app that deliberately intercepts and suppresses it (a known but undocumented technique, reportedly used by apps like Instagram) would prevent that. On Android, the default runs the other way: once a host app has any `WebViewClient` — which an in-app browser cannot function without — every mechanism stays inside the webview unless that `WebViewClient` explicitly hands the navigation to another app. Custom URL schemes and `intent://` links are the weakest choice on both platforms: they depend entirely on host-app code nobody outside Zalo can see, and they fail with crashes or silent no-ops rather than a graceful fallback when unhandled. Universal/App Links are the strongest choice precisely because their worst case is never a dead end — absent app-launch behavior, they simply load as an ordinary web page, on both platforms, regardless of whether the target app is installed.

For the map's mechanism decision: **a Universal Link (iOS) / verified App Link (Android) hand-off is more likely to work from inside Zalo's webview than a custom-scheme or `intent://` hand-off, and it degrades safely even in the worst case.** But whether it *actually* works inside Zalo specifically — rather than merely being permitted by the platform — is a fact only Zalo's closed-source app can determine, and it is not published anywhere. This is exactly the "depends on the host app's own configuration" case the ticket anticipated, and it cannot be closed further from documentation. The map should treat "does the hand-off actually fire inside Zalo" as an open, testable fact, not an assumption in either direction — see the tests below.

## Gaps / open questions

Each item below is a gap — a claim that could not be settled from documentation — not a guess.

1. **Whether a Universal Link to Grab (or Be, or Xanh SM) actually opens the target app when tapped inside Zalo's plain iOS webview.** Apple's documentation says it should by default; whether Zalo's app suppresses this is undocumented and closed-source. **Minimal device test**: on an iPhone (iOS 17 or 18) with the Grab app installed, paste a Grab URL that Grab has registered as a Universal Link (e.g. a promo or profile link) into a Zalo chat to oneself, tap it to open Zalo's webview, then tap a same-page link pointing to that same Universal Link. Observe whether Grab opens, the page loads inline in Zalo's webview, or Safari opens instead.
2. **Whether the equivalent App Link opens Grab/Be/Xanh SM on Android inside Zalo's webview.** **Minimal device test**: same flow on an Android phone (Android 14+) with Grab installed and Grab's App Link domain verified; observe whether Grab opens, a disambiguation dialog appears, or the link loads as a plain web page.
3. **Whether a custom scheme (`grab://open`) or an `intent://` link does anything at all inside Zalo's webview, on either platform.** **Minimal device test**: host a page with two buttons — one linking to a custom scheme the ride app registers (e.g. `grab://open`), one to an `intent://` URL built per Chrome's documented syntax targeting the ride app's Android package — open the page inside Zalo's in-app browser on both an iPhone and an Android phone with the ride app installed, tap each button, and note whether the app opens, nothing visibly happens, an error/toast appears, or the page crashes.
4. **What the Momo redirect thread on Zalo's own developer community actually says.** Neither WebFetch nor the `exa` MCP tools' fetch could render the thread body (`https://developers.zalo.me/community/detail/4899917dad3844661d29`) — it is a client-rendered SPA. **Minimal test**: open the URL in an ordinary desktop browser (which executes the page's JavaScript) and copy the thread body and any staff replies, or ask a member of Zalo's developer community directly.
5. **Whether Zalo's link-preview crawler's User-Agent also contains "Zalo," and could collide with a future server-side detection check.** Not relevant to the client-side JS detection this map actually needs, but worth closing before anyone builds server-side detection later. **Minimal test**: host a small logging endpoint, paste its URL into a Zalo chat without opening it, and inspect the `User-Agent` header of the request that arrives within the following few seconds (the preview-fetch window).
6. **Whether Zalo's in-app browser ever omits or varies its `Zalo iOS/…` / `Zalo android/…` UA token** across app versions or webview modes. **Minimal test**: compare the UA seen from a current Zalo app install against one or two older cached app builds if obtainable, or log the UA seen in production across users' differing Zalo app versions over time, watching for any variant lacking the token.
7. **Whether Grab, Be, or Xanh SM publish an official Zalo Mini App**, which would offer a Zalo-mediated deep-link path (via Zalo's own `openWebview` API) as an alternative to a native OS-level app hand-off. Xanh SM appears to have one, per a Xanh SM social-media post; Grab and Be are unconfirmed. This is a fact about what each ride service offers, not about webview behavior, so it belongs to whichever ticket researches the ride services directly — flagged here only because it surfaced during this pass and would change the mechanism options if true for any of the three services.
